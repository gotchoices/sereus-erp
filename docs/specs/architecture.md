# Architecture: modules, strands and cross-module rules

## 1. Purpose

WyattERP is a set of **modules**. Each module owns one area of the business and is deployed
as its own **Sereus strand** (a shared Quereus database with its own membership and roles).
Modules read each other's data by cross-strand queries, and change each other's data only
through **postings** that the owning module accepts. This replaces ATI's single database, in
which every module could join and update everything.

The aim is to keep ATI's strength (strong constraints, always-consistent data) *inside* each
module, and to get scalability, access control and clear responsibility *between* modules.

## 2. Modules

| Module | Strand | Owns (only this module writes these records) | Typical members |
|---|---|---|---|
| **Catalog** | `catalog` | units, classes, families, versions, minor revisions, parameters, BOM lines, routing, notes and QC criteria, parts and part numbers, standard packages, product documents | engineering, product managers. Read access for most others |
| **Parties** | `parties` | parties (organizations and people), their roles (vendor, customer, shop, employee), addresses, contacts | admin and sales. Read access for most others |
| **Operations** | `ops` | locations, documents (quotes, orders, POs, runs, transfers, adjustments, counts), moves, allocations, lots and serials, run records and QC results, bids, purchasing rounds, posting outbox | purchasing, shop, receiving, shipping, sales |
| **Payables** (AP) | `ap` | vendor invoices, matching against PO lines and receipts, approval for payment, vendor payments and credits | AP clerk, approver for payment |
| **Receivables** (AR) | `ar` | customer invoices (from shipments, jobs and services), credit memos, customer receipts, collections, credit holds | AR or billing clerk, sales manager (read) |
| **Books** (Bonum) | Bonum's strand | the general ledger: accounts and account groups, transactions and entries, tags, periods and closing, bank and other reconciliations, hand journal entries, financial reports. Also the mapping of postings to accounts | the accountant who does the final accounting |
| **Vendor link** | one `vendor:<party>` strand per vendor that participates | that vendor's bids, PO acknowledgments, ship notices | the vendor's people plus purchasing |
| **Shop link** | one `shop:<party>` strand per outside shop that participates | that shop's run status, issues and receipts, QC results | the shop's people plus purchasing and the shop floor |

Starting configuration: catalog, parties, ops and Bonum. AP, AR, vendor links and shop links
come later. Until AP and AR exist, invoices are entered directly in Bonum as ordinary
transactions against the posted control accounts (GRNI, AR), as a small company would do.

**Why AP and AR are separate strands, not part of Bonum.** Strands are the permission boundary
(§8):
* an AP clerk needs vendor invoices, receipts and payments, and not the customer side;
* a billing clerk needs the reverse;
* neither needs to define accounts or close periods.

Bonum remains the accountant's tool, and AP and AR are **subledgers** that post to it, as
operations does. That also keeps Bonum general: it doesn't have to grow ERP modules (Q14, Q26, and November 2026).

## 3. Record ownership

* **Invariant:** every record type has exactly one owning module, and only that module's
  strand stores and writes it.
* Another module that needs to add information about an owned record keeps its **own related
  record**, keyed by the owner's ID. Example: parties owns vendor `V`, ops owns `V`'s bids and
  POs, and AP owns `V`'s invoices and payments. Nobody writes another module's record to annotate it.
* A module MUST NOT copy an owned record in order to change it. It MAY cache a copy for reading
  (for example the storefront's public catalog), marked with the owner's version and
  refreshed from the owner.

## 4. Identifiers and references

* **IDs are opaque text**, generated by the owning module, globally unique (ULID or UUIDv7, so
  they sort by creation time) and never reused. This matches Bonum.
* **Human-facing numbers** are separate fields with their own sequences: part numbers (`1234`),
  document numbers (`PO 24-0153`), run IDs (`R27-014`), serials. They are unique within their
  module and MAY be changed by an administrator. The ID never changes.
* **Cross-module references** carry the target's ID. A reference to a *versioned* catalog
  object also carries the version (`part 1234.3`). Because released versions are immutable, a
  reference that includes the version always resolves to exactly what the referrer saw.
* There are no foreign-key constraints across strands. Instead:
  * the writer checks that the target exists when it writes the reference (by reading the
    other strand);
  * owners never hard-delete a record that might be referenced. They retire it with a status;
  * a **reference check** report per module lists any references it holds that no longer
    resolve.

## 5. Reading across modules

Discussion with Nate (the Sereus maintainer) established that Quereus can already
address several strands and join between them. The working model is:

* A node that belongs to several strands opens them in **one Quereus connection, one schema
  per strand** (`catalog.part`, `ops.move`, `parties.party`…). Queries join across them with
  qualified names. **Not built yet** (checked November 2026): Sereus gives each strand its
  own `Database`, so today a cross-strand read is a join in app code. See
  [../STATUS.md](../STATUS.md) (open items); this section is to be revised after the
  multi-strand spike.
* A node that does not belong to a strand cannot read it. Membership is the coarse access
  control (§8).
* **Planned Sereus enhancement (not assumed for v1):** a read-only **cross-strand view**
  defined in one strand over another strand's data. Nodes that belong to both strands compute
  it. Others know the view exists and can request its contents, and may cache them. WyattERP
  use cases that motivate it:
  * AP seeing receipts and PO lines, for invoice matching, without joining ops;
  * AR seeing shipments and order prices, for billing, without joining ops;
  * a vendor seeing only its own open PO lines;
  * a shop seeing the part definitions, routing and notes for its runs.

  Until it exists, these cases use **published extracts**: the owner writes the relevant
  subset into the link strand (vendor link, shop link) as an explicit step.

## 6. Writing across modules: postings

A module never writes another module's tables. When an event in one module must change
another (a receipt must become a GL entry, for example):

1. In the **same transaction** as the event, the source module writes a **posting** row into
   its own outbox: posting ID, event kind, source document and line IDs, date, amounts and
   quantities, and target module.
2. A **poster** (any member node with the target role) reads unsent postings and applies them
   to the target module, where they become the target's own records (for example a Bonum
   transaction). Each target record carries the **posting ID as its idempotency key**, so
   applying a posting twice has no effect.
3. The poster marks the posting `sent` with the target's record ID. Failures stay `pending`
   with an error message. They are retried and surfaced as alarms.
4. **Postings are immutable.** A correction is a new, reversing posting, never an edit.
5. A **control reconciliation** per pair of modules compares the source's subledger with the
   target's control accounts (for example ops inventory valuation against the Bonum inventory
   accounts) and lists differences.

Planning data never posts (ATI lesson). Only real economic events post: receipts, issues,
completions, shipments, adjustments, scrap, and invoice matches.

**Posting paths:**

| From | To | Events |
|---|---|---|
| ops | Bonum | receipt, issue, completion, shipment, job billing, adjustment, scrap, transform ([operations.md](operations.md) §14) |
| ops | AR | shipment or job completion ready to bill (quantities and prices; AR creates the invoice) |
| AP | Bonum | matched invoice (Dr GRNI and price variance / Cr AP), payment (Dr AP / Cr bank) |
| AP | ops | invoice price variance on stock still on hand (a cost-layer adjustment) |
| AR | Bonum | invoice (Dr AR / Cr revenue, tax), receipt (Dr bank / Cr AR) |
| AR | ops | credit hold on a customer (blocks committing new orders) |

Bonum maps each posting kind to accounts through a configuration that the accountant owns.
Bank reconciliation stays in Bonum.

## 7. Quantities, units and money

* Quantities and money are **exact**. They are stored as integers counting the smallest
  increment of their unit:
  * money in the currency's minor unit, as in Bonum;
  * quantities in units of `1 / 10^scale` of the part's unit of measure, where `scale` is
    defined on the unit (for example meters with scale 3 store millimeters).

  Display divides by the scale.
* The engine computes in floating point and rounds at its boundary (see
  [bom-engine.md](bom-engine.md) §8). Nothing downstream of the engine uses floating point for
  stored values.
* Unit prices may need more precision than the currency's minor unit (for example
  $0.00067 per meter of hose). Unit prices are therefore stored with their own scale (default
  6 decimal places of the currency). Extended amounts round to the minor unit.
* Bonum's `unit` table (type `INVENTORY`) is the eventual meeting point. A part's inventory
  value posts in the reckoning currency, and Bonum MAY also carry its quantity in a
  per-part inventory unit.

## 8. Roles and access

Two layers, replacing ATI's database users, the `priv` table and its per-app views:

1. **Strand membership** decides which modules a person's devices can see at all. Inviting a
   device into a strand is how someone gets a module's interface (Q7: "invite a new
   node to the strand and you have a new user UI").
2. **Roles inside a strand** decide which state transitions a member may make. Each spec lists
   its transitions and the role each one requires. They are enforced in the schema, through
   mutation context, assertions and role-limited views, not only in the UI. This is the
   successor to ATI's views with INSTEAD rules.

Baseline roles (each module refines them): `viewer`, `editor` (create and edit drafts),
`approver` (release, commit, award), `admin` (numbering, roles, retirement). Module-specific
roles are named in each spec (for example `buyer`, `receiver`, `shop`, `engineer`).

## 9. History, audit and immutability

* Every row carries `created_at`/`created_by` and `updated_at`/`updated_by`.
* **Immutable once final:** released catalog versions, minor revisions, done moves, closed
  documents, postings and run records. They are corrected by new records (a new version, a
  reversing move, a reversing posting), never by an edit.
* Editable records whose history matters (bids, part stock policy, notes before release) keep
  an append-only **history table**. ATI's `vend_price_hist` is the model.
* "Alarm" notifications for exceptional events (ATI kept these) are records in the module that
  raised them, readable by subscribed members.

## 10. Schema evolution

* Each module's schema is declared with Quereus `declare schema` and changed by
  `diff`/`apply` migrations that **preserve data**. Rebuild-on-change, which Bonum does today,
  is not acceptable here.
* Each module has a schema version. Postings carry the source schema version, so a poster can
  refuse a format it does not understand.

## 11. Shared libraries

The packages live under `packages/` in this repository. Apps (under `apps/`) are thin layers
over them.

* `@wyatt/bom-engine`: the parametric BOM engine ([bom-engine.md](bom-engine.md)). It is a
  pure library with no storage of its own, used by every interface, by back-end jobs and, if
  useful, registered in Quereus as a deterministic scalar function (Quereus supports
  synchronous `createScalarFunction` with a `deterministic` flag). Other computational modules
  that come later get their own specifically named packages, not a general "engine".
* `@wyatt/domain`: shared types, quantity and money arithmetic, ID generation and partname
  parsing.
* `@wyatt/core`: the control logic for each module's strand: its schema, queries, writes,
  role-checked transitions, outbox and poster. It is handed a running Sereus node and never
  builds one; apps do that. Any app that works in a module's strand goes through this package,
  so the strand's rules live in one place (see §5 and [../STATUS.md](../STATUS.md) on apps
  sharing strands).

## 12. Performance notes

ATI's ledger reached 2.9 million moves, and Bonum has found that the Quereus store pays per-row
cost on ranges and aggregates. So:
* balances and planning figures are **maintained** (materialized views or explicitly
  maintained tables), never computed by scanning the move history on each read
  ([operations.md](operations.md) §6);
* documents in a final state stop contributing to planning queries;
* very old done moves MAY later be archived into period summaries. **Open:** not needed at
  the startup's volume.
